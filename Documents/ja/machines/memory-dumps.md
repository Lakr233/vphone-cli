# メモリダンプ

メモリダンプは、実行中のゲストのメモリとプロセッサの状態を Mac 上のファイルに保存します。LLDB や独自のツールでオフライン解析するためのものです。メモリのコピー中はゲストが一時停止し、その後そのまま動作を続けます。

## ダンプを保存する

1. 仮想マシンのウィンドウで **Diagnostics > Save Memory Dump…** を選びます。
2. フォルダを選びます。その中に、`myphone Memory 2026-11-19 at 15.20.11` のようにマシン名と時刻を付けた新しいフォルダが作成されます。
3. ダンプの保存先を知らせるアラートが表示されるまで待ちます。ゲストが一時停止するのは最初の部分だけで、通常 10〜20 秒です。ファイルの書き込み中はゲストが再び動作しており、書き込みにはさらに 1 分ほどかかることがあります。

ターミナルからは、マシンの[制御ソケット](create-and-run.md#制御ソケット)に、作成するフォルダを指定して `memory.dump` を送ります。そのフォルダはまだ存在していてはならず、親フォルダは存在している必要があります。

```sh
printf '%s\n' '{"t":"memory.dump","path":"/Users/me/Dumps/myphone-1"}' | nc -U ~/.vphone/machines/myphone/vphone.sock
```

応答はファイルの書き込みが終わってから返ります。各ファイルのサイズと実際に保持しているバイト数、キャプチャと書き込みにかかった時間が含まれます。`vphone-launchpad-cli guest send` は 2 分で待つのをやめるため、8 GB の書き込みにそれ以上かかる Mac では上のように `nc` を使ってください。

## ダンプの内容

| ファイル | 内容 |
| --- | --- |
| `AP.core` | カーネルの仮想アドレスで見たゲストの RAM、vCPU 上で実行中だったプロセスのユーザメモリ、すべての vCPU の汎用レジスタ |
| `SEP-coproc.core` | Secure Enclave のメモリ（約 20 MB） |
| `info.json` | マシン、時刻、vphone と macOS のバージョン、各ファイルのサイズ |

どちらのコアも Mach-O のコアファイルです。LLDB は `AP.core` をそのまま開き、vCPU ごとにスレッドを表示します。

```sh
lldb -c "myphone Memory 2026-11-19 at 15.20.11/AP.core"
```

`thread list`、`register read`、`memory read`、`bt` はほかに何も用意せずに使えます。シンボルを使うには、ゲストが起動したカーネルキャッシュを追加し、`target modules load --file <kernelcache> --slide <slide>` でゲストの KASLR スライドにロードします。

ダンプには、物理アドレス、変換テーブルのベースやポインタ認証キーなどのシステムレジスタ、カーネルがマップしていないメモリは含まれません。

## 容量と時間

- `AP.core` はゲストの RAM より少し大きく、8 GB のゲストでは 8.6 GB です。すべてゼロのブロックはファイルから省かれるため、APFS ボリュームではデータ分の容量しか使いません。通常はゲストの RAM の大部分です。
- ボリュームの空き容量がゲストの RAM より少し多い量に満たない場合、ゲストを一時停止する前に保存を中止します。
- ゲストの一時停止中、macOS はそのメモリのコピーを保持します。メモリに余裕のない Mac では、一時停止と書き込みに時間がかかります。
- 一時停止中はゲストの時計が止まります。ゲストが再び動き出すとすぐに、`vphone-vm` がゲストの時計を Mac の時刻に戻します。
- 1 台のマシンについて、同時に保存できるダンプは 1 つです。

ダンプには、Virtualization フレームワークがメモリコアを書き出せる macOS が必要です。macOS 27.2 は対応しています。対応していない macOS ではメニュー項目が使用できず、`memory.dump` はその旨を返します。

ダンプの作成方法と測定結果については、[`Research/Host/memory_dump.md`](../../../Research/Host/memory_dump.md) をご覧ください。
