# 20. `pathleak` порциями: перебор inode через `fsgetpath()` без блокировки главного потока

Дата: 2026-11-26. Подзадача «pathleak chunked» из треда jailbreak. Статус: код написан и проверен на Mac, на устройствах не запускался.

## 1. Исходная точка

Оригинал — `tools/pathleak.m` (GPLv3, forcequitOS), описание техники — в `ios26-kernel-research/sandbox-escape.md`, раздел «pathleak — Container Enumeration».
Идея: у файловой системы, на которой лежит контейнер, перебираются номера inode `1..max_inode`, для каждого вызывается
`fsgetpath(buf, size, &fsid, inode)` (`<sys/fsgetpath.h>`, iOS 11+), и пути, начинающиеся с нужного префикса, собираются в массив.
Это обходит необходимость знать случайный UUID контейнера.

Проблема оригинала: один цикл на весь диапазон. По данным задачи `max_inode` ≈ 300 000 000 (iPhone 13) и ≈ 90 000 000 (iPhone 17 Pro Max),
полный проход занимает минуты, а процесс может быть убит через несколько секунд — результат теряется целиком.

## 2. Что сделано

Порционная версия: `pathleak_chunked.h` / `pathleak_chunked.m` (48 + 176 строк, Foundation + `<sys/fsgetpath.h>` + `<sys/mount.h>`, без внешних зависимостей).
Лежит вне репозитория: `/Users/i_strelov/Projects/vphone/pathleak_chunked/`. В `tools/` не переносилась — в `tools/` остался оригинальный `pathleak.m/.h`.

| Функция | Назначение |
|---|---|
| `pathleak_scanChunk(dir, from, to, progressEvery, progress)` | один синхронный проход по `[from, to)`; `progress(done, found)` раз в `progressEvery` итераций и в конце порции |
| `pathleak_scanAsync(dir, from, to, chunkSize, interval, progress, completion)` | `dispatch_source`-таймер на главной очереди; каждые `interval` секунд запускает порцию в последовательной фоновой очереди; `completion(paths, error)` один раз на главной |
| `pathleak_takeResults()` | забрать накопленное и очистить буфер (потокобезопасно, `os_unfair_lock`) |
| `pathleak_reset()` | очистить буфер |
| `pathleak_stop(handle)` | прервать обход; `completion` придёт с ошибкой «Обход остановлен» |

Отличия от оригинала:
- префикс канонизируется через `realpath()` (`fsgetpath` отдаёт канонический путь: `/tmp/...` → `/private/tmp/...`; с префиксом-симлинком оригинальный фильтр давал 0 совпадений);
- фильтр тот же: `prefix + "/" + имя без "/"`, то есть только непосредственные дети `dir` (сам подкаталог включается, его содержимое — нет);
- ошибок `statfs`/`realpath` нет: обе функции молча возвращают 0 найденного.

**На устройствах (iPhone 13 / 17 Pro Max, Basil VM) — ничего.** Код туда не переносился и не запускался.
Числа 300M / 90M и «процесс убивается через несколько секунд» — исходные данные задачи, мной не замерялись.

**На этой машине (macOS 26.5, APFS, Xcode 26.5 SDK):**

| Проверка | Результат |
|---|---|
| Скорость `fsgetpath` | ≈ 3–3.6 мкс на вызов (0.3 млн/с): 2 млн inode ≈ 7 с, 20 млн ≈ 60 с. 300 млн ≈ 17 мин чистого времени |
| Отсутствующий inode | `-1`, `errno=ENOENT` (2), буфер не заполняется |
| Чужой fsid | `-1`, `errno=45` (`ENOTSUP`) |
| Буфер 4 байта | `-1`, `errno=28` (`ENOSPC`) |
| Каноничность пути | `fsgetpath` вернул `/private/tmp/...` для каталога в `/tmp`; сравнение с префиксом `/tmp/...` — 0 совпадений, с `/private/tmp/...` — совпадения есть |
| Номера inode на APFS (Mac) | свежесозданные файлы ≈ 752 5xx xxx (больше 2³²); корень тома — inode 2 |
| Компиляция `pathleak_chunked.m` | чисто с `-Wall -Wextra` под macOS SDK и под iphoneos SDK (arm64) |
| Прогон `scanAsync` | каталог с 5 файлами и подкаталогом `sub/deep.txt`, диапазон ±200 000 вокруг inode каталога, `chunkSize=80000`, `interval=0.05`: 5 порций, `progress` после каждой, `completion` один раз, найдены 5 файлов + `sub`, `sub/deep.txt` отфильтрован |
| Прогон `pathleak_stop` | остановка через 0.3 с: `completion` с ошибкой «Обход остановлен», 2 тика до остановки |

## 4. Известные ограничения

- **Общий статический буфер.** Результат один на процесс; два параллельных `scanAsync` (даже на разных каталогах) смешают результаты.
- **Нет `NSError` из `pathleak_scanChunk`.** `statfs`/`realpath` отказали — порция молча вернёт 0, асинхронный обход завершится с пустым массивом и `error == nil`. Это главный дефект API.
- **Прогресс в `scanAsync` — раз в порцию, а не раз в N итераций.** Внутри порции `progressEvery` не используется (передаётся 0): колбэк нельзя звать с фоновой очереди. Для более частого прогресса уменьшать `chunkSize` (10 000 inode ≈ 35 мс на Mac).
- `progress(done)` считает `next - from` — inode, запущенные в работу, а не завершённые; расхождение до одной порции.
- `ENOTSUP` не прерывает порцию (в раннем наброске прерывал; убрано, чтобы перебор соседних томов на macOS не заканчивал обход раньше времени).
- Результат только в памяти: при убийстве процесса накопленное теряется, сохранения на диск нет.
- Цикл retain (`scan` ↔ таймер) разрывается только в `finishWithError`; при незавершённом обходе объект живёт до `pathleak_stop` или исчерпания диапазона.
