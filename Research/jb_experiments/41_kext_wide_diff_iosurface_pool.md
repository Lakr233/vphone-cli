## 3. Проверка доступа к пулу: 23F84 vs 23G83

Строки в кексте (grep -a по файлу):

| Строка | 23F84 | 23G83 |
|---|---|---|
| `IOSurfaceMemoryPool: %s (%d) can't access pool id %llu (wrong entitlements)` | есть | есть |
| `IOSurfaceMemoryPool: %s (%d) invalid task (%p) can't access pool id %llu (wrong entitlements)` | **нет** | есть |
| `taskCanUsePool` | нет | есть |
| `pool off limits for poolId 0x%llX` | нет | есть |

**23F84, `0x98be138` (99 ins), вызывающие:**
- `0x98affbc` (67 ins): `x0 = pool`, `x1 = x21`
- `0x98b3304` (305 ins, `create_surface`): `x0 = x26` (pool), `x1 = [x23+0xf8]`

Тело: `x1 == [x0+0x30]` или `x1 == *(0x7f0e560)` → вернуть 1. Иначе `f(0xa572674)(x1, "com.apple.private.iosurfaceinfo")`; если не 0 → retain и вернуть 1. Иначе лог «can't access pool id» → 0.

**23G83, `0x98c7494` (118 ins), вызывающие:**
- `0x98bbb70` (67 ins) — тот же сайт, что `0x98affbc`
- `0x98beeb8` (305 ins, `create_surface`) — тот же сайт, что `0x98b3304`, `x1 = [x23+0xf8]`
- **`0x98c7384` (`newWiredMemoryDescriptorWithLength`): `x0 = pool` (результат `0x98c5c54(x1=аргумент x3)`), `x1 = аргумент x4`** — новый сайт

Тело: `x1 == NULL` → лог + 0. `x1 == [x0+0x30]` или `x1 == *(0x7f12478)` → 1. Иначе `f(0xa581398)(pool, x1)` (это `IOTaskHasEntitlement`-обёртка: `x0==NULL` → текущая задача; строка-ключ `0x7b3cc10` — пустая по `kcx`, имя entitlement'а не восстановил); при успехе — retain, 1. Иначе лог «invalid task» → 0.

### Что здесь не так в моей же расшифровке

Аргументы в таблице выше — `x0`, `x1` в момент вызова. Во всех сайтах `x0` — объект пула, `x1` — **число**
(poolId), это согласуется с `cmp x1, [x0+0x30]` и с форматом `%llu`. Но дальше та же `x1` уходит в
`IOTaskHasEntitlement(pool, x1)`, где второй аргумент должен быть задачей. Либо `0xa572674`/`0xa581398` — не
`IOTaskHasEntitlement`, либо в `x1` лежит не число. **Назначение второго аргумента я не установил**; читать
«проверка entitlement'а задачи» нельзя.

## 4. Новый сайт в `newWiredMemoryDescriptorWithLength` (23F84 `0x98bb7d0`)

23F84: `x1 = x3` → `bl 0x98ba0a0` → pool; `cbz pool → NULL`; сразу `bl 0x98bb880(pool, x1, x2, x4, x5)`.
23G83: между ними `x1 = x4 (сохранён в x25)`, `bl taskCanUsePool`, `tbz → лог + NULL`.

Внутри `0x98bb880` (395 ins, тело в обоих билдах одинаковое) `x28 = x4`:
- `0x98bb96c`: если аллокация `0xa4687d0(1)` не удалась и `x28 != 0` → переход на `0x98bbb98`
- `0x98bbb98`: `ldr x16,[x28]`, `autda`, `ldr x8,[x16,#0x28]!`, `blraa x8` — **виртуальный вызов на `x4`**, затем `retab` с `x0 = x24` (NULL)
- нормальный путь: `str x28,[sp+0x10]`, `ldp x25,x28,[sp+8]` (после этого `x28 = 0`)

В `allocate` (23F84 `0x989a20c`): `x3 = [uc+0x330]` (poolId), `x4 = [uc+0x170]`. То есть `x4` — поле
userclient'а, а не значение из словаря клиента. `[uc+0x170]` пишется только в `init` (`0x9895f30`, `0x989607c`)
и очищается в `0x989a910`. Что туда попадает в `init` — **не проверено** (стр. 75–84 `pool_new.dis`).

- 24B156 (iPhone 17 Pro Max) не смотрел: есть ли третий вызов там, неизвестно.
- Кексты из §1, кроме IOSurface, не разбирались. `com.apple.kernel` (93 изменённых) — заметка 27 покрывает только часть.


## 7. Дополнение (вечер 2026-11-27): IOSurface закрыт частично, найден второй кандидат — AppleMatch (regex sandbox)

### 7.1 IOSurface: что установлено твёрдо

- `0x7f12478` (IOSurface `__got`) → `0x7b3cc10` ядра `__DATA_CONST,__const`: внутри vtable (вокруг — PAC-указатели на
  методы), в промежутке из четырёх нулевых слотов. Значение слота — 0. В `taskCanUsePool` (23G83) ветка
  «`x1 == *(0x7f12478)` → разрешено» на практике означает «`x1 == 0` → разрешено», но новая ветка «`x1 == 0` → лог
  invalid task → отказ» стоит **раньше** неё. Иначе говоря, в 23F84 `x1 == 0` проходил как разрешённый; в 23G83 тот же
  случай сперва попадает в лог с «invalid task» и возвращает 0. Это единственная логическая разница тел, которую я могу
  показать по инструкциям. Точный смысл `x1` не установлен (см. следующий пункт).
- `surface+0x170` (аргумент `x4` в `newWiredMemoryDescriptorWithLength`) пишется в `IOSurface::init` (`0x98a1ae0`,
  вызывающий — `create_surface_internal` `0x98b8e8c`): это **результат `OSObject`-вызова на properties-словаре** с ключом
  `"IOSurfacePixelSizeCastingAllowed"`. Это **не** объект пула, как я писал в §4. Что именно возвращается — не установлено.
- Аргумент `x1` проверки — **число** poolId (`cmp x1,[this+0x30]`, формат `%llu`). Дальше оно уходит вторым аргументом в
  `0xa572674`/`0xa581398`, похожую на `IOTaskHasEntitlement`, где вторым аргументом должна быть задача. **Противоречие не
  разрешено.** Обе интерпретации неверны хотя бы в одной точке.

**Вывод по IOSurface: кандидат остаётся открытым, но не доказан; приоритет понижен.**

### 7.2 AppleMatch: изменённые функции — regex-движок, единственный клиент — Sandbox.kext

`com.apple.kext.AppleMatch` — regex-движок (строки `site.struct __matchExpr`, `reNFA_t.reGraphNode_t`, `rePackedNFA_t`).
Кросс-кекстовые вызовы (скан `bl` по всем 249 кекстам, `f41/crosscalls.py`): только `com.apple.security.sandbox` —
4 вызова, из них `0x9bca0c4 → 0x8b4329c` (функция-компилятор, 1289→1292 ins).

| 23F84 → 23G83 | Инстр. | Правка |
|---|-|---|
| `0x8b3a0dc` → `0x8b4329c` | 1289→1292 | `str xzr,[sp,N]` (обнуление локальной) + перестройка записи заголовка записи |
| `0x8b3b500` → `0x8b446cc` (grow) | 53→77 | см. ниже |
| `0x8b3b5d4` → `0x8b44800` | 71→115 | вместо прямого `bl grow` — проверка «запись попадает в буфер 1 или буфер 2» (проверка границ через `[+0x30]/[+0x38]`, `[+0x40]/[+0x48]`) и только затем grow; после grow — пересчёт указателя |

Рост буфера (`grow`), 23F84:
- `count = [this+0x20] + 10`; `cap16 = u16[this+0x60]` (**в кексте нет ни одной записи в `+0x60`**); `cap = 0x3fffffff / count`
  (деление на `count`: при `count == 0` результат не определён); если `count > cap` → 0
- `size = count * cap16 * 2`; `kalloc(size, 4)`; проверки `size >= count*[+0x38]` и `size - count*cap16 >= count*[+0x48]`, иначе `brk #0xbffe`

Рост буфера (`grow`), 23G83:
- `cap16 = max(2*u16[+0x28], [+0x38]+1, [+0x48]+1, 1)`, затем `min(cap16, 0xffff)`
- `x25 = [+0x20] + 10`; **если `x25 == 0` → отказ**; `cap = 0x3fffffff / x25`; `cap16 > cap` → отказ
- дальше та же арифметика, но `cap16` — вычисленное, не прочитанное

Что это значит: в 23F84 ёмкость нового буфера брали из поля `+0x60`, которое в кексте никто не пишет; в 23G83 её
вычисляют из текущих `count`/`cap1`/`cap2` и ограничивают `0xffff`. Это форма фикса «непроверенная ёмкость → маленький
буфер под больше записей». **Но** является ли `+0x60` в 23F84 неинициализированным или OOB-полем — не установлено: размер
объекта и его аллокатор не найдены (функции без прямых вызывающих, vtable-ссылок через chained-fixup не нашёл —
декодер `kcptr.py` даёт target как низкие 30 бит, я искал с этой маской и не нашёл).

### 7.3 Досягаемость AppleMatch из приложения — не проверена

Вызывающий в Sandbox: `0x9bca058` (51 ins) → вызывается из `0x9bc6200` (3191 ins, строки профиля `com.apple.rootless.
restricted-block-devices`, `truncated`, `K_INFO`) — это **компиляция sandbox-профиля**. Передаётся `x1` — структура
профиля (`u16` на `+0x46` — число regex в профиле), индекс `x3`, буфер `x4`/`x5`. То есть regex приходит **из профиля**,
а не от приложения. Какой процесс на 23F84 может подсунуть свой профиль в ядро — не проверял (`sandbox_init` с
кастомным профилем, `containermanagerd`, `.sb`-файлы из TrustCache). **Ответ — в заметке 42:** нужен entitlement `com.apple.private.sandbox.profile` (`:embedded`), для стороннего приложения путь закрыт.

### 7.4 sandbox / AMFI — мелкие правки, не кандидаты

  ответа container-manager'а, не security-проверка.
