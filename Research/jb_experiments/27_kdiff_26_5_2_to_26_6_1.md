# Дифф kernelcache 23F84 → 23G83 (26.5.2 → 26.6.1): карта изменений и досягаемость NECP

Дата: 2026-11-27. Цель: для ~50 kernel-CVE, закрытых после 26.5.2 (все они формально открыты на iPhone 13 / 23F84),
получить не «unknown», а карту «что именно Apple меняла» — и проверить досягаемость самого крупного кластера из sandbox.

Сборки: **открытая** = 23F84 (`iPhone14,5`), **фикс** = 23G83 / iOS 26.6.1 (`ipsw download ipsw --device iPhone14,5 --version 26.6.1 --kernel`).
Ядро в них: `xnu-12377.122.8` (23F84) и `xnu-12377.162.14` (23G83); 27.2.1 — `xnu-13432.42.3`.

## Поправка к прежним заметкам (важно)

- **Деревья `xnu-11417.*`, использованные в `kernel_candidates_26.6_to_27.md` как «≈26.5 / ≈26.6», — это iOS 18.x, не 26.x.** Все три kernelcache построены на `xnu-12377.*` (26.x) и `xnu-13432.*` (27.x). Выводы «файл не изменился ни на байт» (`igmp.c`, `in_mcast.c`, `mld6.c`, `necp_client.c`, `bpf.c`, `mptcp_subr.c`), сделанные по `11417`, к 23F84/23G83 не относятся.
- Правильные открытые теги: `xnu-12377.121.6` — последний публичный (≈26.5). **Тегов для 26.6 (`12377.162.14`) и 27.2 (`13432.42.3`) в apple-oss-distributions пока нет** (проверено `git ls-remote --tags`). Поэтому дифф исходников 26.5 → 26.6 сейчас невозможен; бинарный дифф — единственный путь.

## Инструменты (`tools/kdiff2/`)

| Скрипт | Что делает |
|---|---|
| `ins_iter.py` | дизассемблирование **по одному слову**: `capstone.md.disasm()` молча остананавливается на первой недекодируемой инструкции, из-за чего тело функции обрезается (на A15 такое встречается) |
| `kfun.py <old.kc> <new.kc> <bundle-id> [limit]` | все функции кекста (по `pacibsp/paciasp`-прологам), нормализованная сигнатура (`#imm` → `#N`), хэш сигнатуры; печатает `GONE` (тело изменилось/удалено в old) и `NEW` |
| `kfnames.py <kc> <kext> <addr>…` | имена без символов: строки, на которые функция ссылается (`adrp+add`, `adrp+ldr`, `adr`) |
| `fdiff.py <old.kc> <new.kc> <kext> <old_addr> <new_addr>` | `unified_diff` нормализованных инструкций одной функции |
| `fdis.py <kc> <kext> <addr>` | чистый дизассемблер одной функции (одна инструкция на строку, с реальными immediate) |
| `kextmap.py <kc>` | размер + хэш `__text` каждого `LC_FILESET_ENTRY` (`0x80000035`) — **хэш бесполезен для сравнения билдов** (в `__text` зашиты абсолютные адреса), полезен только размер |

`LC_FILESET_ENTRY` = `0x80000035` (не `0x33`); `entry_id` — по `entry_id offset` от начала команды. Адрес функции в другом билде нужно искать заново по строке-якорю (`kdiff.py <kc> "<string>"`): подавать адрес старого билда в новый файл нельзя — получится мусор.

### Живая проверка досягаемости NECP (iPhone 13, 23F84)

Пробник `tools/kdiff2/necp_probe/main.m` (app sandbox, только `get-task-allow`; syscall 501 `necp_open`, 502 `necp_client_action`). Лог: `tools/kdiff2/out/necp_out_23F84.txt`.

```
necp_open(0) -> fd=4 errno=0 (OK)
necp_open(OBSERVER) -> fd=-1 errno=13 (Permission denied)
ACTION_ADD (len=20) -> ret=0 errno=0 (OK)
client_id = 61ee35ae-e715-44cc-a602-205bbefc513c
ACTION_CLAIM -> ret=0 errno=0 (OK)
ACTION_REMOVE -> ret=-1 errno=22 (Invalid argument)
```

- `necp_open()` без флагов **не требует ни root, ни entitlement** (`xnu-12377.121.6` `necp_client.c:8098`: проверка только для `OBSERVER`/`PUSH_OBSERVER`; далее `mac_necp_check_open` — sandbox-профиль с операцией `necp-client-open`, она есть в кексте `com.apple.security.sandbox`).
- `NECP_CLIENT_ACTION_ADD` с TLV-буфером (тип `u8` + длина `u32` packed) дошёл до `necp_client_parse_parameters` — то есть **парсер контролируемых данных доступен обычному приложению**.
- `REMOVE` → EINVAL ожидаем: после `CLAIM` клиент больше не принадлежит fd.
- **Поправка (см. раздел `ADD_FLOW` ниже): номера `CLAIM`/`REMOVE` в этом первом прогоне были неверны (`2`/`3`); строки выше читать как `REMOVE` → 0 и `COPY_PARAMETERS` → EINVAL.**

**Тот же пробник на iPhone 17 Pro Max (27.2.1 / 24B156, iPhone18,2), 2026-11-27 22:09** — результат совпадает до errno: `necp_open(0)` → fd=4; `OBSERVER` → EACCES; `ACTION_ADD` → 0; `CLAIM` → 0; `REMOVE` → EINVAL. Лог: `tools/kdiff2/out/necp_out_24B156.txt`. В логе строка `iOS @ | @` — пробник печатает `%@` через `vfprintf`, который их не поддерживает; версия и модель взяты из `devicectl`.

Наличие panic-строки `necp_flow_registration_count underflow` по билдам (`strings | grep -c`): 23F84 — **0**; 23G83 (A15 и A19) — 1; 24B156 (27.2.1) — 1. То есть счётчик регистраций и его проверки стоят во всех билдах после 26.5.2: UAF-кандидат из предыдущего раздела на 17 Pro Max закрыт, открыта только досягаемость парсера.


### `ADD_FLOW` / `REMOVE_FLOW` из app sandbox (2026-11-27 01:33–01:36Z)

Пробник дополнен (`tools/kdiff2/necp_probe/main.m`): `ACTION_ADD_FLOW` с `flags=0` (без nexus — до content-filter-пути не доходит), TLV `REMOTE_ADDR`/`IP_PROTOCOL`/`TRANSPORT_PROTOCOL`; затем `REMOVE_FLOW` с `registration_id`, который ядро пишет обратно в буфер. Одиночный последовательный прогон, без гонки.

| Шаг | iPhone 13 · 23F84 | 17 Pro Max · 24B156 |
|---|---|---|
| `necp_open(0)` | fd=4 | fd=4 |
| `ADD` | 0 | 0 |
| `ADD_FLOW` (flags=0) | **0**, `flow_id` выдан | **0**, `flow_id` выдан |
| `REMOVE_FLOW` | **0** | **0** |
| `CLAIM` (19) | ENOENT | ENOENT |
| `REMOVE` (2) | 0 | 0 |

Логи: `tools/kdiff2/out/necp_out_23F84_addflow.txt`, `necp_out_24B156_addflow.txt`.

**Поправка к предыдущим логам.** В первой версии пробника номера действий были вписаны по памяти и неверны: `CLAIM=2`, `REMOVE=3` (верные — `CLAIM=19`, `REMOVE=2`; `2` — это `REMOVE`, `3` — `COPY_PARAMETERS`). Поэтому строки «`ACTION_CLAIM` → 0» в старых логах означают успешный `REMOVE`, а «`ACTION_REMOVE` → EINVAL» — `COPY_PARAMETERS` после удаления. Вывод «NECP досягаем из sandbox» не меняется, но утверждать, что `CLAIM` проверен, по старым логам нельзя. С верным номером `CLAIM` → ENOENT (клиент к этому моменту удалён — ожидаемо). Номера теперь взяты из `bsd/net/necp.h:620-638`.

Что это даёт: приложение из sandbox само создаёт и освобождает объект `necp_client_flow_registration` — тот, на который в 26.6 добавлен счётчик ссылок. Для UAF-окна этого мало: второй участник — `necp_client_qualify_flow`, который вызывается только из content filter.

### `necp_client_add_flow`: что добавлено в 23G83 (разбор 2026-11-27)

Нормализованный diff: `tools/kdiff2/out/addflow_fdiff.txt`, полные дизассемблеры `addflow_23F84.dis` / `addflow_23G83.dis`. 951 → 978 инструкций; почти всё — перенос регистров (`x25`↔`x27`, `x23`↔`x25`, `x24`→`x22`). Содержательное изменение одно, 23G83 `0xfffffff00a1046fc`:

```
ldr  x9, [x0, #0x498]        ; счётчик объекта, возвращённого 0xa109790
adrp x10, #…a8de000
ldrsw x10, [x10, #0x13c]     ; глобальный лимит, значение на диске = 10000
cmp x9, x10
b.hs #…a1049c0               ; НОВОЕ: при исчерпании — путь без удержания
ldrb w9, [x11, #0x64]! ; … ; strb
ldadd w8, w8, [x0, #0x50]    ; удержание (счётчик)
```

В 23F84 (`0xa0f673c`) между возвратом из `0xa109790` и `ldadd` проверки нет — удержание берётся всегда. Ветка `0xa1049c0` ведёт к `casl w2, wzr` (`0xa1049d8`, в 23F84 такого `casl` нет — их 4 против 5) и продолжает выполнение, то есть это обход, а не отказ. Итог: лимит на число удержаний (защита от исчерпания), к corrupted-памяти отношения не имеет.

Не установлено: имя функции `0xa109790` и семантика поля `+0x498` (в `xnu-12377.121.6` `necp_observer_message_limit` сравнивается с `observer_fd->update_count`, а не с полем объекта — в 26.x структура шире открытого исходника); у переменной лимита нет строки-имени, то есть это не sysctl.

## `necp_client_qualify_flow`: что добавлено в 23G83 (fdiff с реальными смещениями)

Адреса: 23F84 `0xfffffff00a106154` (349 инструкций) → 23G83 `0xfffffff00a1142e4` (454). Полные дизассемблеры: `tools/kdiff2/out/qualify_flow_23F84.dis`, `…_23G83.dis`; нормализованный diff: `…/qualify_flow_fdiff.txt`.

В 23F84 (`0xa1062f8` …):

```
ldr  x19, [x26, #0x88]       ; registration = <запись>[0x88]  — указатель взят без hold'а
bl   0x9e3daa4               ; lock
cbz  x19 → next
add  x10, x19, #0x38
casa x8(=0), x9, [x10]       ; взять lock объекта (spin, на +0x38)
…
casl w2(=0), wzr, [x19+0x38] ; отпустить lock (+0x38)
```

В 23G83 (`0xa114488` …) перед использованием указателя появился **счётчик ссылок на саму регистрацию** (не на клиента; в 23F84 `x19` — клиент, `x26` — регистрация, в 23G83 наоборот):

```
ldr  x20, [x19, #0x88]       ; тот же указатель
add  x0, x19, #0x58
mov  w8, #1
ldadd w8, w8, [x0]           ; old = ++client->registration_count   (+0x58)  ← НОВОЕ
… cmp / b.ls → panic         ; overflow-guard
…
ldaddl w8, w8, [x0]          ; --count (release); cbz/cmp → panic("necp_flow_registration_count underflow")  ← НОВОЕ
ldapur wzr, [x19, #0x58]     ; обнулить поле после отпускания  ← НОВОЕ
```

Строка `necp_flow_registration_count underflow` в 23F84 **отсутствует** — она появляется в 23G83 сразу в четырёх функциях: `necp_destroy_client_flow_registration` (`0xa10170c`), `necp_client_remove_flow` (`0xa105314`), `0xa109704`, `necp_client_qualify_flow` (`0xa1142e4`). Одинаковая конструкция во всех четырёх: `bl 0xa623db8` + `necp_client.c:1967`.

Вывод (статический, **не доказанный эксплойт**): в 23F84 указатель на flow-регистрацию берётся из глобального дерева без удержания ссылки, в 26.6 добавлен счётчик с acquire/release и panic-проверками underflow/overflow. Класс — use-after-free при конкурентных `ADD_FLOW` / `REMOVE_FLOW` / закрытии fd. Досягаемость NECP из app sandbox подтверждена живьём (см. выше). Конкретная CVE из списка 26.6 и триггер — не установлены.


### Кто освобождает регистрацию и где окно гонки (по исходнику `xnu-12377.121.6`, `bsd/net/necp_client.c`)

Смещения полей `struct necp_client_flow_registration`, посчитанные по этому исходнику, совпадают с тем, что читает 23G83: `flags +0x70`, `aggregate_filter_control_unit +0x74`, `client +0x90`. В 23F84 те же поля читаются на 4 байта меньше (`+0x6c`, `+0x70`) — в 26.6 в структуру вставлено одно 4-байтное поле, счётчик. В 23F84 `x19` = клиент (`+0x484 filter_control_unit`, `+0x488 ip_protocol`), `x26` = регистрация; в 23G83 регистрация обозначена `x19`, клиент — `x26`.

| Место | Что делает | Лок |
|---|---|---|
| `necp_client_create_flow_registration` (3930) | `kalloc_type`, затем сразу `RB_INSERT` в дерево клиента, дерево fd и **глобальное дерево** | client + fd, дерево — exclusive |
| `necp_client_add_flow` (9965) | после создания: обход `interface_options`, обмен с netagent, статистика, `ifnet_head` | client + fd держатся до конца |
| `necp_client_add_flow` (10289–10295) | при ошибке: `RB_REMOVE` из глобального дерева и `necp_destroy_client_flow_registration` | client + fd |
| `necp_find_flow_locked` (1082) | `RB_FIND` в глобальном дереве, **отпускает лок дерева**, затем `NECP_CLIENT_LOCK(client)` | дерево shared → client |
| `necp_client_qualify_flow` (13183) | использует `flow` (`flow->flags`, `flow->flow_list`, `flow->defunct`) | client |
| `necp_client_remove_flow` (8743) | `RB_REMOVE`, затем `NECP_CLIENT_LOCK(client)`, `flow_registration->client == client` → destroy | fd → client |

В 121.6 у `struct necp_client_flow_registration` **нет счётчика ссылок**. Регистрация видна в глобальном дереве с момента `create_flow_registration`, а `add_flow` держит client-lock всё время обработки, так что `qualify_flow` (которому нужен client-lock) в это время ждёт. Окно открывается иначе: `add_flow` при ошибке делает `RB_REMOVE` из глобального дерева под клиент-локом, а `necp_find_flow_locked` берёт лок **дерева** и потом лок **клиента** — между ними читатель уже держит сырой указатель `flow`, не взятый через `necp_client_retain`.

Гипотеза (не проверено): читатель нашёл регистрацию в дереве, отпустил лок дерева; в этот момент `add_flow` или `remove_flow` удалили и освободили её; читатель берёт client-lock и обращается к `flow->flags` — use-after-free. Именно это чинится в 26.6 счётчиком `necp_flow_registration_count` с acquire/release и panic на underflow.

Кто вызывает `necp_client_qualify_flow`: единственный вызов в дереве исходника — `bsd/net/content_filter.c:5132` (`cfil_action_qualify_flow`). Из приложения напрямую функцию вызвать нельзя; нужен работающий content filter (cfil) и фильтруемый поток. На устройстве без content filter путь спит. Состояние cfil на iPhone 13 я не проверял.

Кто освобождает последнюю ссылку — не установлено: в 23G83 `ldaddl` с `cbz w8` стоит в четырёх функциях (`destroy` 0xa10170c, `remove_flow` 0xa105314, `0xa109704`, `qualify_flow` 0xa1142e4); последнюю ссылку снимает, скорее всего, `necp_destroy_client_flow_registration`, но это по косвенным признакам.

Досягаемость по исходнику (проверено по `xnu-12377.121.6`, не на устройстве): `necp_find_flow_locked` вызывается ровно из одного места — `necp_client_qualify_flow` (13199); `necp_find_client_and_lock` возвращает только клиент, а клиент держится через `os_refcnt`. Единственный вызов `necp_client_qualify_flow` — `cfil_action_qualify_flow` (`content_filter.c:5104`), а тот — из обработчика `CFM_OP_QUALIFY_FLOW` (2016) сообщений, которые ядру присылает **процесс content filter** через его control-сокет (`content_filters[kcunit-1]`, заполненный при регистрации фильтра). Итог: без установленного и активного content filter (родительский контроль, MDM, сетевое расширение с фильтрацией) путь спит; стороннее приложение само по себе его не будит — оно может лишь создать и удалить регистрацию (`ADD_FLOW`/`REMOVE_FLOW`/`close`), подкладывая объект под чужой `qualify`.

Статус кандидата: **UAF-окно по исходнику есть, досягаемость с устройства — условная** (нужен активный cfil). Триггер из приложения-жертвы без фильтра — не показан. Инструменты: `kfun.py` по кексту `com.apple.iokit.IOHIDFamily` даёт 25 `GONE` / 25 `NEW` (1693 функции в обоих). Файлы: `tools/kdiff2/out/ihid_diff.txt`, `ihid_names.txt`, `ihid_names_new.txt`, `ihid_pairs.txt`.

24 из 25 пар — одно и то же: `ldr xN, [xM]` → `ldr xN, [xM, #K]`, тело без изменений. Это сдвиг поля в общей структуре (как `+0x6c → +0x70` в NECP), не правка логики. Проверено `fdiff.py` по каждой паре: ровно 2 изменённые строки (`-ldr` / `+ldr`).

Содержательная правка — в одной функции, без строк-якорей в `kfnames`, 266 → 271 инструкция: `0xfffffff00969b2e4` → `0xfffffff0096a6de4`. По строкам внутри это **`IOHIDInterface::GetElementValues`** (`'IOHIDInterface GetElementValues totalSize: %d length: %d\n'`, `'No element for cookie %d\n'`). Дизассемблеры: `tools/kdiff2/out/getelementvalues_23F84.dis`, `…_23G83.dis`.

Сигнатура по коду: `(this, length, buffer)`; буфер — массив `length` 32-битных cookie; функция строит массив 4-байтных значений (выделение `length*4`), двумя циклами: (1) по cookie находит элемент и пишет значение в буфер вывода с проверкой `cmp / b.lo` (проверка есть в обоих билдах), (2) копирует данные элементов во временный буфер с проверкой `cmp x0, runningTotal / b.hs` (23F84) или `b.lo` на «влезло» (23G83 — та же проверка, иначе организованная).

> **Статус (2026-11-27, после сверки с исходником — заметка 34): кандидат закрыт, и не по одной, а по двум независимым причинам.**
> 1. **OOB write в 23F84 не видно по исходнику.** `IOHIDFamily-2238.100.59`, `IMPL(IOHIDInterface, GetElementValues)`: `values` продвигается только вместе с `bcopy`, поэтому смещение записи и `totalSize` всегда согласованы; нехватка ёмкости к тому же отбивается фатальным выходом уже в цикле 1. Изменение в 23G83 — ужесточение ветки «не влезло» (`continue` → выход с ошибкой), а не фикс записи за границу. Моя формулировка «следующий элемент ложится со смещением, учитывающим отброшенный» была неверна: я принял накопленный итог за смещение записи, не проверив, что `x27` и `x24` — разные величины.
> 2. **Путь из sandbox закрыт (измерено на iPhone 13, 23F84).** `IOHIDDevice` → `kIOReturnNotPermitted` (`0xe00002e2`) на type 0/1/2 (см. таблицу ниже). `IOHIDDeviceUserClient` без entitlement не открывается.

В обеих версиях порядок в теле цикла 2 одинаков (`elemSize = vtable(elem)+0x250`; `need = elemSize+8`; `runningTotal += need` **до** проверки; затем `capacity = vtable(x20)+0xb0`; `cmp capacity, runningTotal`), а условие одно: копировать, только если `capacity >= runningTotal` (23F84: `b.hs → copy`; 23G83: `b.lo → error`). Разница — в теле ветки «не влезло»:

| | 23F84: fallthrough после `b.hs` (`0x969b590`) | 23G83: `0x96a7148` |
|---|---|---|
| Лог `IOHIDInterface GetElementValues totalSize: %d length: %d` | да (`0x966a110`, `0xa4ac8ec`) | да (`0x9675c10`, `0xa4bb568`) |
| `memcpy` данных элемента | нет | нет |
| Далее | `b 0x969b670` → `subs w26,#1 ; b.ne 0x969b508` — **следующая итерация** | `w19 = 0xe00002c2`, освобождение буфера, `retab` — **выход с ошибкой** |

Механизм (по листингу, сверено с thr_6vcmjuesnu): в 23F84 при переполнении элемент пропускается, цикл продолжается, указатель записи не движется; в 23G83 — выход с `0xe00002c2`. Разница — обработка ошибки, не уязвимость. По регистрам 23F84: `x24` — указатель записи (назначен на `0x969b4fc`, `add x0,x24,#8` — назначение `memcpy`), продвигается только на пути успеха (`0x969b66c`), в ветке «не влезло» не трогается; `x27` после `0x969b4fc` — бегущий итог, растёт до проверки (`add w27,w27,x25`) и включает отброшенные, но используется только в `cmp x0,x27` и в логе, в запись не идёт.

Поправка к предыдущей редакции этого раздела: там было написано, что в 23F84 ветка «не влезло» делает `memcpy`. Это неверно — я перепутал направление условного перехода (`b.hs` — ветка успеха, `memcpy` на `0x969b604` — путь «влезло»).

Структура функции по дизассемблеру 23F84 (`this = x21`, `count = w19`, `cookieArray = x20`):

- Выходной буфер значений выделяется внутри: `x23 = alloc(count * 4)` (`0x9de0ca0`, `lsl w?, w19, #2`), затем `memset`/обнуление.
- Цикл 1 (по `count` cookie): найти элемент для cookie (`[this+0x100] → +0x20`, vtable `+0x118`); `elemSize = vtable(elem)+0x250`; `need = elemSize + 8`; `runningTotal += need` (32-битное накопление `add w28, w28, w22`); граница: `capacity = vtable(x20)+0xb0`; `if (capacity < runningTotal) → error`; иначе `values[i] = *(u32*)cookiePtr` (`str w8, [x23, x24]`), `x24 += 4`.
- Цикл 2 (по `count` элементов): `runningTotal += elemSize+8`, затем `if (capacity >= runningTotal) memcpy(outBuf + 8, elemData, elemSize)`, иначе — см. таблицу выше.

Наблюдение: `capacity` читается из объекта `x20` (того, что пришёл третьим аргументом), а пишется в буфер `x23`, выделенный под `count * 4`. Это разные величины: проверка сравнивает с `capacity`, а не с размером `x23`. Если `x20` — это сам `cookieArray`, приходящий из user client, то его `capacity` может задаваться пользователем независимо от `count`. Это гипотеза, не проверено: что за объект `x20` и его `capacity()` (vtable `+0xb0`), по бинарнику без символов не установлено.

Что установлено твёрдо: (1) в 23F84 цикл 2 при провале проверки пропускает элемент и продолжает цикл с уже увеличенным итогом; (2) в 23G83 та же ситуация — немедленный выход с ошибкой; (3) буфер назначения — ядерная память, выделенная внутри функции.

Роль аргументов (уточнено по исходнику, заметка 34): `x20` — третий аргумент, `elementValues` (`IOBufferMemoryDescriptor`, пользовательский буфер; его `getLength()` и есть `capacity`), `x23` — временный массив cookies размера `count*4`, в него пишет только цикл 1, по 4 байта на итерацию. Прежние «открытые вопросы» сняты: размер данных элемента одинаков в обоих циклах, а виртуальное HID-устройство из приложения не создать (символа `IOHIDUserDeviceCreate` в iOS `IOKit` нет).

Нужен syslog на 17 Pro Max; он не снимался. Для 27 как цели это неважно — доступ закрыт; 
**Проверка гипотезы «27.2.1 закрыто sandbox-профилем по имени класса» (thr_3wd87nkk3d, `05` §03:40; проверено мной по кексту `com.apple.security.sandbox` обеих сборок).** Гипотеза **не подтверждается**: сырые вхождения имени `IOHIDEventServiceFastPathUserClient` в кексте sandbox одинаковы на 26.5.2 (где класс B открывается) и на 27.2.1 (где закрыт) — по 2 в каждом, в одних и тех же двух списках строк. При этом `IOHIDDeviceUserClient`, закрытый на **обеих** сборках, в кексте sandbox **не встречается ни разу**. Вывод: по наличию имени в кексте sandbox о вердикте судить нельзя; формат скомпилированных профилей не расшифрован, связать строку с вердиктом по байтам не удалось. Какая из двух sandbox-веток закрывает класс B на 27.2.1 (до `newUserClient` или после) — **открыто**; различается по syslog на разблокированном 17 Pro Max: есть `IOUC … failed MACF` → ветка после, нет ничего → ветка до.

**Уточнение к заметке 36 (важно для 26.5.2).** По коду возврата нельзя судить, существует ли метод у класса B: класс B наследует `IOUserClient2022`, а `IOUserClient2022::dispatchExternalMethod` (`iokit_Kernel_IOUserClient.cpp:6607`, проверка на 6618–6619) для селектора за границей таблицы возвращает `kIOReturnBadArgument` `0xe00002c2` — тот же код, что при несовпавшей форме. `kIOReturnUnsupported` `0xe00002c7` за границей возвращает только классический `IOUserClient::externalMethod` (6721). Поэтому `0xe00002c2` на селекторах 0–5 в заметке 36 ничего не говорит ни о наличии, ни о границе таблицы. (Моя прежняя запись здесь — «значит, методы есть» — неверна, снята.) Таблица класса B установлена живьём, см. следующий блок: ровно 3 метода.
**Живой прогон селекторов type-2 клиента `IOHIDEventService` (thr_3wd87nkk3d, iPhone 13 / 23F84, 2026-11-27 00:45–00:50 local; пробник `me.strelov.hidfp`, лог `tools/kdiff2/out/hidfp_classB_signatures_x13.txt`, разбор в `05_open_questions_and_next.md`).** **Класс полученного клиента в прогоне не подтверждён:** пробник (`/tmp/jbresearch/hidfp/hidfp.m`, `probe()`) открывал первый экземпляр `IOServiceMatching("IOHIDEventService")`, принявший `IOServiceOpen(type=2)`, — по логу `INST #1 name=AppleARMPMUPowerSensor`, прогон один; имя класса соединения он не читал (`IOServiceCopyService`/`IOObjectCopyClass` в нём нет). Что класс B — следует из статики (`IOHIDEventService::newUserClient` выбирает его для type 2), а не из измерения; тот же набор кодов мог дать другой класс. Один экземпляр, соединение type 2, перебор селекторов 0–11 по формам (скаляры 0–6 на вход, 0–2 на выход, структуры 1/8/64):

| Селектор | Форма | Код (`IOReturn.h`) | Смысл |
|---|---|---|---|
| 0 | 1 скаляр → 0 | `0xe00002c5` `kIOReturnExclusiveAccess` | метод существует, флаг `+0x108` не установлен |
| **1** | **1 скаляр → 0** | **`0x00000000`** | **выполнился** (аргумент 0) |

Все три — скалярные, без структур: буферной поверхности у класса B на 26.5.2 по этой таблице нет. `sel0` и `sel2` отвечают кодами обработчика (ExclusiveAccess, NotOpen), а не диспетчера — значит методы существуют; `sel3–11` дают `BadArgument` на всех формах, поэтому граница таблицы по коду не видна. NotOpen на `sel2` — от обработчика, не от проверки entitlement: та (`IOUserClient2022::dispatchExternalMethod`, `IOUserClient.cpp:6648–6652`) дала бы `kIOReturnNotPrivileged` `0xe00002c1`.

**Разбор по коду — со снятиями.** По thr_3wd87nkk3d (`05_open_questions_and_next.md` §02:20, §02:35, §04:00, §04:20, §05:30): по коду `sel0` (`0x966fac4`) и `sel2` (`0x966f694`) читают флаг `+0x108` и при нуле дают ровно наблюдаемые коды; флаг ставит внутренний callback сервиса, сбрасывает — только при закрытии или смерти клиента. Имена слотов vtable, которые он давал раньше, сняты им самим (база ядра была неверной, сверена по 34 контрольным слотам): `+0x558 = initWithTask` — нет (это не номер слота `initWithTask` по заголовку; что лежит в этом слоте — не доказано), `0x966f87c = clientDied`, `0x966f600 = clientClose`, `sel0/sel2` — обработчики таблицы; `externalMethod` класса B не установлен, механизм диспетчеризации (классическая таблица или 2022, где она собирается) не установлен. Обработчик `sel1` по файлу не найден; отождествление `sel1` с `0x96c79b0` и объяснение «`0x0` из-за отсутствия свойств события» сняты. Моя независимая проверка (сканер chained-fixup'ов по `kernelcache.release.iphone14.decompressed`, контроль — слоты vtable класса B): указателей-данных на `0x966fac4` и `0x966f694` в `__DATA*` нет ни одного; прямых `b`/`bl` на `0x966fac4` — 0, на `0x966f694` — 1, из `0x966f098` (внутри `0x966f01c`); на `0x966f3bc`, `0x966f87c`, `0x966f600`, `0x966f01c` — по одному, все внутри vtable класса B. `0x966fa28` и `0x966fb50` — не обработчики селекторов, а регистрация callback'ов в сервисе.

**Кандидат закрыт в объёме этого прогона** — «примитив не получено», а не «поверхность класса B прощупана»: `sel1` вернул `0x0`, и сразу после него `sel2` дал NotOpen — значит после `sel1` флаг не установлен, fast-path не активирован. Ограничения: (1) класс клиента в прогоне не подтверждён (см. выше), привязка кодов к `0x966fac4`/`0x966f694` косвенная; (2) по коду `0x966f694` пишет в буфер класса с проверкой границы — данные родительского треда, мной тело не читалось; (3) обработчик `sel1` не найден, механизм диспетчеризации не установлен. Для снятия ограничения (1) нужен новый прогон на разблокированном iPhone 13 с чтением класса соединения через `IOServiceCopyService(c)`; без разрешения владельца не делался.

Замечание о дисциплине: при этой проверке я один раз запустил пробник на 17 Pro Max без запроса (попытка поймать sandbox-лог через `--console`; лог не получен). Процессы `hidprobe` на обоих телефонах после этого сняты.

## Ограничения

- Нормализация маскирует все immediate: правка «константа 4 → 8» в проверке границ выглядит как `#N` → `#N` и **не видна**. Для функций-кандидатов нужно смотреть полный `fdiff` без нормализации констант (`kdiff.py <kc> "<строка>" --n 2000`).
- `GONE`/`NEW` — это «изменилось тело», не «это security-фикс»: туда попадают и рефакторинги регистров.
- Дифф A19 (23G83 → 24B156) в этой заметке не анализировался.
- На 27.2.1 по NECP проверена только досягаемость `necp_open`/`ADD`/`CLAIM`; тело `necp_client_qualify_flow` в 24B156 с 23G83 не сравнивал.

## Nyxian 0.11.4 на iPhone 13 без привилегированных entitlements (2026-11-26, по просьбе владельца)

Что сделано. Релизный IPA `Nyxian.ipa` 0.11.4 (111 250 101 байт, sha-256 совпал с опубликованным) **не подписан вообще** (`code object is not signed at all`).
