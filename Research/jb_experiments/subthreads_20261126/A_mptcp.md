# Задача A: воспроизвести баг MPTCP (кандидат CVE-2026-86962) на iPhone 13, затем проверить 27.2.1

## Цель
Живым тестом на iPhone 13 (26.5.2 / 23F84) установить, воспроизводится ли описанный в публичном отчёте дефект MPTCP, и получить **безопасный** (без паники) наблюдаемый признак срабатывания — ответ `MP_FAIL` от устройства. Затем, если удастся, то же на iPhone 17 Pro Max (27.2.1 / 24B156), начиная с наименее опасного варианта.

## Первоисточник (прочитай целиком, это главный вход)
`/tmp/jbresearch/pubsrc/mptcp_report.md` (576 строк), PoC-сервер `/tmp/jbresearch/pubsrc/mptcp_dfin_reach.py` (767 строк, scapy, режимы `dfin`, `zero_spray`, `csum_uaf`, `chain_deref`), клиент `/tmp/jbresearch/pubsrc/mptcp_client_v2.c`.

Суть из отчёта (перескажи себе сам по тексту, здесь только ориентир): DSS-сегмент с `data_len=1`; если `dlen` становится 0 до цикла извлечения из очереди сокета, `mptcp_validate_csum` вызывается на mbuf, который ещё числится в `so_rcv`; при плохой контрольной сумме он освобождается. Включение проверки контрольной суммы — битом `MPCAP_CHECKSUM_CBIT` в SYN-ACK сервера (по отчёту).

## Что уже проверено статически (перепроверь сам по листингам, прежде чем опираться)
- 23F84: в `mptcp_subflow_soreceive` (по прежнему анализу — `0xfffffff00a20c3e4`) при `dlen==0` переход `0xa20c744 → 0xa20c974`, вызов validate — `0xa20cb34 ldr x1,[x29,#-0x60]` → `bl 0xa1fe204`.
- 24B156: блок отключения mbuf перед validate (по прежнему анализу — `0xfffffe000b0508fc`) выполняется только при `DATA_FIN ∧ dlen==0 ∧ dsn==1`; при `DATA_FIN=0` пропускается. Что происходит при `DATA_FIN=0 ∧ dlen==0` на 24B156 — **не установлено**.
- Открытый исходник: `/tmp/jbresearch/igmp/xnu/full/xnu-12377.121.6/bsd/netinet/` (`mptcp_subr.c`, `mptcp.c`, `mptcp_opt.c`, `mptcp_usrreq.c`). Из `mptcp_usrreq.c:222` `mptcp_entitlement_check` отказывает только для `MPTCP_SVCTYPE_AGGREGATE`; тип 0 (`HANDOVER`) по умолчанию — `ГИПОТЕЗА`, что приложение без entitlement может открыть такой сокет и подключиться.

## Чего делать НЕЛЬЗЯ
- Режимы PoC, рассчитанные на **панику** (`dfin`, `zero_spray`, `csum_uaf` со спреем), на устройствах не запускать. Устройство должно остаться работоспособным; если оно всё же ушло в панику/перезагрузку — зафиксируй это и остановись, не повторяй. Вариант `DATA_FIN=1` не запускать ни на одном устройстве, включая 17 Pro Max (там он, по прежнему анализу, должен быть закрыт, но риск перезагрузки устройства владельца — не твоё решение).
- Не отправлять ничего на чужие хосты: сервер — только наш (см. ниже), клиент — только наши устройства.
- Не менять настройки сервера (firewall, ssh, systemd, ufw, nginx). Исключение ровно одно: на выбранном хосте может понадобиться **один** входящий TCP-порт для PoC-сервера. Прежде чем его открывать, прочитай в репо freehire-ops, как на этом хосте устроен firewall (облачный firewall Hetzner, ufw), открой порт тем же способом, которым там оформлены правила, по минимально широкому источнику, который позволяет тест (если firewall хоста поддерживает указание источника — укажи внешний IP телефона; узнать его из ответа/лога клиента, если не получится — так и напиши). Запиши точную команду/изменение и **закрой порт после теста**, восстановив исходное состояние. Если для открытия порта нужно менять то, что в репо описано как управляемое terraform — не меняй, а вернись с этим вопросом.

## Порядок работы
1. **Подготовка сервера.** Linux-хост — из инфраструктуры freehire-ops. Репозиторий с описанием сети: `/Users/i_strelov/Projects/freehire/freehire-ops` (локальный чекаут может отставать — сделай `git fetch` и читай `provision/NETWORK.md` в актуальной ревизии, либо прочитай его на сервере). Хосты: core `136.243.174.114`, operator `89.167.94.146`, ops `204.168.137.149`, hydra `204.168.174.129`, все `root`, ключ ed25519. Выбери хост для PoC-сервера по правилу: наименее важный для продакшена, есть python3 и возможность поставить scapy в venv без системных изменений. По описанию — кандидат `hydra` (side projects), но реши по факту: проверь `uptime`, свободную память, наличие python3/venv, что на хосте уже слушает. Свои файлы клади в `/root/jbresearch-mptcp/`. Перед первым действием запиши в заметку, какой хост выбран и почему.
2. **Транспорт PoC.** Готовый скрипт рассчитан на L2 (`sendp`, `iptables`). Телефон и сервер — в разных сетях. Перепиши PoC так, чтобы он работал на IP-уровне (raw-сокет / обычные сокеты с нужными TCP-опциями) и слушал на **одном** TCP-порту. Сохрани как отдельный файл `mptcp_ip_server.py` рядом с оригиналом (оригинал не менять). Проверь его на двух Linux-хостах freehire-ops между собой (сервер на одном, обычный TCP-клиент с MPTCP-опцией — на другом), пока поведение не совпадёт с ожидаемым по коду: SYN → SYN-ACK с `MPCAP_CHECKSUM_CBIT` → ACK → DSS `data_len=1` без DATA_FIN и с плохой суммой.
3. **Клиент на iPhone 13.** Собери пробу в `/tmp/jbresearch/wq_x13/` (см. «Процедура»): `socket(AF_MULTIPATH, SOCK_STREAM, 0)` + `connectx()` к `IP:порт` сервера; после установки соединения отправить 1 байт, ждать ответа ~2 с, залогировать: возвраты вызовов, `errno`, результат `recv`. Константы — как в `mptcp_client_v2.c` (`AF_MULTIPATH 39`, `connectx`). Если `socket()` вернул ошибку — это тоже результат (запиши `errno`); попробуй тип сервиса 0 (по умолчанию) и 1 (`INTERACTIVE`), тип 2 (`AGGREGATE`) — не пробовать. В лог пиши каждый шаг до вызова.
4. **Тест на iPhone 13.** Запусти сервер в режиме **без DATA_FIN, без спрея, без RST сразу** (безопасный вариант по отчёту: «Experiment 4/5»). Признак срабатывания — `MP_FAIL` (subtype 6) от телефона в дампе на сервере. Один запуск = одна попытка. После каждой попытки: проверить, что устройство живо (`xcrun devicectl device info details --device …`, нет новых panic-файлов в `systemCrashLogs`), залогировать. Максимум 3 попытки с DFIN=0. **Вариант с DATA_FIN=1 не запускать** на 23F84 — по отчёту это паника.
5. **Если шаг 4 дал MP_FAIL** — запиши pcap и логи. Это будет подтверждением, что на 23F84 путь выполняется. Расширение (спрей для перехвата слота, чтение и т.п.) — **не делать**, только описать как следующий шаг.
6. **iPhone 17 Pro Max** (если доступен): только безопасный вариант (DFIN=0), максимум 3 попытки, тот же критерий MP_FAIL. Если MP_FAIL пришёл — на 27.2.1 путь `DFIN=0` выполняется (при этом повреждение памяти не доказано). Если нет — разберись по дампу, на каком пакете оборвалось (RST от телефона и т.п.), и запиши.
7. **Статика по ходу** (если останется время): для 24B156 установи по листингу, что при `DATA_FIN=0 ∧ dlen==0` mbuf остаётся связанным с `so_rcv`/`sb_lastrecord` на момент вызова validate — или нет. Инструменты — в общих правилах.
8. Восстанови `/tmp/jbresearch/wq_x13/wqprobe.m` к виду `/tmp/jbresearch/wq2/wqprobe.m`, пересобери, переустанови на iPhone 13. Сервер на Linux-хосте останови, venv и файлы можно оставить в `/root/jbresearch-mptcp/`, открытый порт закрой.
