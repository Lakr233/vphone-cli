## 1. Verdict: hypothesis **refuted** (wrong CVE id for this component)

The advisory lists each entry as `Component → Impact → Description → CVE: credits`. Read in order
(`IOMobileGraphics` … `IOGPUFamily` … `IOMobileFrameBuffer` … `Kernel`):

| Component | Impact | Description | CVE |
|---|---|---|---|
| **IOGPUFamily** | Processing maliciously crafted **web content** may lead to memory corruption | improved memory handling | **CVE-2026-64788** — anonymous researcher, f00l (@PPPF00L), 3ndy1 (@_3ndy1), Minghao Lin (@Y1nkoc), 云散花折, Arjanit Isufi |
| **IOMobileFrameBuffer** | An **app** may be able to cause unexpected system termination or corrupt kernel memory | out-of-bounds access, improved bounds checking | **CVE-2026-64736** — Ruslan Dautov, hxr1 |

So the IOMFB out-of-bounds fixed in 26.6.1 is **CVE-2026-64736**. CVE-2026-64788 is the IOGPUFamily
web-content bug (consistent with `iogpu_family_65346_86944.md` and with lightsword's
`iogpu_uaf64788.m`; the `iomfb_probe{,_v2,_v3}.m` files are blind selector sweeps, not PoCs).
`apple_advisory_entries_26.5.2_to_27.2.1.md` rows 64/122 carry the same mix-up and need the same fix.

Secondary point: 24B156 is **iOS 27.2**, three releases after the 26.6.1 fix. A 26.5.2 ↔ 27.2 diff
cannot attribute a change to 26.6.1. Any "fix" claim from that pair is unproven.

4. **Relaxed-check selectors**: `0x9733ba4` special-cases four selectors by copying their entry to the
   stack and overwriting `checkScalarInputCount` with `args->scalarInputCount` and
   `checkStructureOutputSize` with `args->structureOutputSize`, so the kernel helper's exact-match
   checks pass for *any* scalar count / output size: **0x44 (68)** (`0x97348fc`, struct in 0x100),
   **0x4e = set_block**, **0x4f = get_block**, **0x55 = get_block_buf**. That is why their table counts
   are zero: the wrappers validate arguments themselves. For get_block / get_block_buf the caller-chosen
   output size is therefore only bounded by the callee (see §3).
5. **AP vtable location**: the provider object (`UC+0xd8`) is a class of
   **`com.apple.driver.AppleMobileDispH14P-DCP`**: vptr `0xfffffff007d1e220` (twin `0x7d1ee00`), in that
   kext's `__DATA_CONST.__const`. `+0x718` set_block `0x970cfec`, `+0x720` get_block `0x970d1d8`,
   `+0x728` `0x970d34c`, `+0x850` `0x8b9127c` (get_block pbt 0x80), `+0x930` set_block_dcp `0x971bf88`,
   `+0x938` get_block_dcp `0x971c170`, `+0x690/0x698/0x6a0` notify `0x970dd04/0x970df08/0x970e044`.
   The earlier "`0x7eca820` in IOMFB" anchor was wrong; the function IDs stand.

## 3. What is bounded in 23F84 (so not the 64736 bug)

- **set_block (0x4e)**: wrapper needs `scalarInputCount >= 2` and non-NULL input struct; scalars
  `[0]=pbt, [1]=first index, [2..]=more indexes`, struct = block bytes (`structureInputSize` = block_size).
  Gate `isSetBlockEnumAllowed` (`0x9732238`, clientType `UC+0x104`). AP `set_block` → `map_block_buf`
  (`0x970cb84`) checks `block_size >= max(addr_offs+8, size_offs+4)` (else `0xe00002bc`) before reading
  the pointer/size fields → `set_block_dcp` (`idx_count < 9`, `block_size <= 0x1000`).
- **get_block (0x4f)**: wrapper needs non-NULL output, `scalarInputCount >= 2`, passes
  `structureOutputSize` through. `get_block_dcp` (`0x971c170`): `idx_count <= 8`, `out_size <= 0x1000`
  (else `0xe00002c2`), DCP exchange with a 0x1004-byte reply buffer, copies exactly `out_size` bytes
  into the kernel's copy-out buffer of the same size. No OOB either side.
- **set_notify (0x48)**: `ilk <= 7` (`cmp w3,#7; b.ls`), 8 × 0xb0-byte entries at `UC+0x110` → ends `0x690`,
  inside the 0x698-byte UC object. 27.2 widens this to `ilk <= 11` / 12 entries, i.e. a capacity change,
  not a missing bound in 26.5.2.

Not reviewed: `get_block_buf` (0x55) body, the `+0x850` pbt-0x80 handler's callee (`vt[+0x688]`), the gain-map
path (0x56), selector 0x44 and the 0–0x3a range.
