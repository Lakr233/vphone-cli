# 36. IOHID: что на самом деле открывается по `IOServiceOpen(…, type=2)` на `IOHIDEventService`

Дата: 2026-11-27. Объект: iPhone 13 (A15, iOS 26.5.2 / 23F84), физическое устройство. Пробник `tools/hid_fastpath/` (bundle `me.strelov.hiddev`, wildcard-профиль, только `get-task-allow`, sandbox по умолчанию; селекторы вызываются только скалярные, без структур и без выходных буферов). Лог: `tools/hid_fastpath/out_13_23F84.txt`.

Зачем: `07` и `tools/hid_probe` зафиксировали «`IOHIDEventService` открывается с type 2 из sandbox», а `28`/`35` и `27` оставляли открытым, какой это класс и есть ли у него guard. Это определяло, досягаемы ли CVE-2026-43739/43816 (OOB write в `IOHIDEventServiceUserClient`).

## Результат

| Вопрос | Ответ | Чем доказано |
|---|---|---|
| Что открывается по `type=2` | **`IOHIDEventServiceFastPathUserClient`**, а не `IOHIDEventServiceUserClient` | `newUserClient` в 23F84: `cmp w3,#'esuc'` → класс A; иначе `cmp w3,#2` → класс B; всё остальное → `super` (Unsupported). `initWithTask` класса B читает строку `com.apple.hid.system.user-access-fast-path` |
| Досягаем ли `IOHIDEventServiceUserClient` (CVE-…43739/43816) | **Нет** | создаётся только по `type='esuc'` (`0x65737563`); `initWithTask` без entitlement `com.apple.hid.system.user-access-service` возвращает false → `IOServiceOpen` возвращает `BadArgument` |
| Guard у FastPath-клиента | **мягкий**: без entitlement клиент всё равно создаётся | ветка «не совпало» в `initWithTask` не выходит: лог «is not entitled», флаги `+0x118=0`, `+0x119=0`, далее `str x20,[x21,#0xd8]`, canary, возврат true |
| Сколько экземпляров | 64 `IOHIDEventService` (11 PMU power, 16 PMU temp, ~21 SPU HID, touch, prox, NVMe temp, кнопки, …) + 3 `IOHIDEventDriver`; все 67 открываются по type 2 | живой прогон |

Ответ слепых вызовов селекторов 0–5 (только скаляры, без структур): `0xe00002c2` (`kIOReturnBadArgument`) на всех 67. Устройство не паниковало. По таблице ниже это ожидаемо для всех: у 0 и 2 структура обязательна, у 3–5 — номер за пределами таблицы.

### Таблица методов (23F84, `__DATA_CONST,__const`, `0xfffffff007eb2528`, 3 записи по 0x28 байт)

Найдена по адресу селектора `open` (см. ниже), который в неё записан закодированным указателем. Формат `IOExternalMethodDispatch2022` (`IOUserClient.cpp:6624`): функция, затем `checkScalarInputCount`, `checkStructureInputSize`, `checkScalarOutputCount`, `checkStructureOutputSize`; `0xffffffff` — размер не проверяется.

| Сел. | Функция | Скаляров in | Структура in | Скаляров out | Структура out |
|---|---|---|---|---|---|
| 0 | `0x96c7388` | 1 | любая | 0 | 0 |
| 1 | `0x966efd4` | 1 | 0 | 0 | 0 |
| 2 | `0x966f01c` | 2 | любая | 0 | любая |

### Что делают методы (по дизассемблеру)

- **Селектор 0** (`0x96c7388`): `structureInput` (`[args+0x30]`, размер `[args+0x38]`) десериализуется через `0xa4a67d8` (`OSUnserializeBinary`, по сигнатуре `buf, len, NULL`); нулевой указатель или нулевой размер → `0xe00002c5`. Результат и первый скаляр (`[[args+0x20]]`) передаются в `0x96c79b0`. Успех → бит `+0x10a` = 1.
- **`0x96c79b0`** (реализация `open`):Ветки возврата (все три дочитаны): `[this+0xe0] == 0` → лог `open not ready`, код `0xe00002bd + 0x1a = 0xe00002d7`; бит 0 байта `+0x108` или байта `+0x109` установлен → лог `open already opened`, код `0xe00002bd + 8 = 0xe00002c5`; нет ключа в словаре → лог `open missing properties`, код `0xe00002bd + 5 = 0xe00002c2`. Дальше: бит 0 байта `+0x118` выбирает GOT-слот кекта (`0x7eb0008` при 1, иначе `0x7eb0000`); взятый из него объект принимает вызов vtable `+0x100` (`x0 = словарь, x1 = ключ`), `cbz w0` → «missing properties». Название вызываемого метода по бинарю не установлено; успех → `+0x10c` = аргумент, `+0x109` = 1 (открыт, ставится самим `open`). Кто ставит бит `+0x108.0` и что в ветке `+0xe0 == 0`, не разобрано.
- **Селектор 1** (`0x966efd4`): вызывает у себя vtable `+0x5d8`, затем сбрасывает бит байта `+0x10a`. Это `close`.
- **Селектор 2** (`0x966f01c`): `structureInput` десериализуется тем же `0xa4a67d8`; если второй скаляр (`[[args+0x20]+8]`) равен 1 — вместо этого вызов `0xa46c9b4`. Объект уходит в `0x966f694(this, obj, scalar[0])`, счётчики `+0x128`/`+0x12c` увеличиваются, результат возвращается. Внутри `0x966f694` проверка `0xa4f99e4` (сбой → `0xe00002be + 0x19`), затем работа с провайдером `[this+0xe0]` через его vtable (`+0x668`, `+0xe0`, `+0x140`). Это чтение события; пользовательских длин, индексов и смещений в разобранном куске нет, но функция разобрана не до конца (первые ~60 инструкций из 122).

### Живой вызов `open`: проходит из sandbox

Пробник `tools/hid_fastpath/out_13_23F84_sel0_success.txt` (iPhone 13, 26.5.2): селектор 0, 1 скаляр, `structureInput` — бинарный plist со всеми ключами класса (`FastPathHasEntitlement`, `FastPathMotionEventEntitlement`, `opened`, `openedByClient`, `copycount`, `errcount`, `suspendcount`, `ExternalMethod`), значения `true` и `1`, новое соединение на каждую попытку, **0 выходных скаляров и без выходной структуры** — как требует таблица.

| Ответ | Экземпляров | Что это по коду `open` |
|---|---|---|
| `0x00000000` | 4 из 64 | `open` прошёл; все четыре — `AppleSPUHIDDriver` |
| `0xe00002c5` | 60 из 64 | «already opened» (`+0x108.0` или `+0x109`): сервис уже держит клиент |

Устройство не паниковало. Минимальный нужный набор ключей не выяснялся — испытывался только полный список.

**Поправка к прежним версиям этой заметки.** Ранние вызовы возвращали `0xe00002c2` на всех экземплярах, и я приписал это ветке «missing properties». Это было неверно: я передавал 1 выходной скаляр при `checkScalarOutputCount = 0`, и вызов отбивал диспетчер (`IOUserClient.cpp:6636`), до метода дело не доходило. Выводы «словарь не содержит ключа», «проверка по entitlements процесса» и весь разбор поиска ключа через GOT-слоты сняты — они сделаны по вызову, который не выполнялся.

## Что из этого следует

- Поверхность FastPath-клиента **открыта** из sandbox без entitlement: `open` проходим на свободных сервисах `AppleSPUHIDDriver`.
- Остались два метода с реальной обработкой пользовательских данных: `copyEvent` (сел. 2: 2 скаляра + структура любого размера) и `open` при уже открытом сервисе. Что делает `copyEvent` с входным словарём — не разобрано дальше первых 60 инструкций `0x966f694`.
- Правило для всех следующих проб: счётчики скаляров и размеры структур должны строго совпадать с таблицей диспетчеризации, иначе ответ приходит от диспетчера, а не от метода. Инструмент `tools/kdiff2/kdisp.py` даёт эти значения по любому кексту.
- На iPhone 17 Pro Max (27.2.1 / 24B156) та же поверхность закрыта жёстко: `IOServiceOpen(…, type=2)` → `0xe00002e2` (`kIOReturnNotPrivileged`) на всех 78 экземплярах (`/tmp/jbresearch/hidev/out_17.txt`).

## Не получилось

- Не разобран `copyEvent` (`0x966f694`) после первых ~60 инструкций и не выяснено, какой минимальный словарь нужен `open`.
- Таблица символов kernelcache вырезана (`nsyms = 0` в `LC_SYMTAB` записи `com.apple.kernel`), поэтому имена функций ядра по адресу не восстановить: `ksym.py` бесполезен на этом образе.
- Xref-сканером `adrp+add` находится не каждый reference на строки `__os_log`.

## Инструменты

- `tools/hid_fastpath/` — пробник (перебор всех экземпляров, имя класса, результат type 0/1/2, скалярные селекторы 0–5).
- `tools/kdiff2/fdis3.py <kc> <kext> <va> [n]` — дизассемблер файла кекта по словам.
- `tools/kdiff2/esuc.py <kc> <kext> <FourCC hex>` — поиск материализации 32-битной константы (`movz+movk`) в `__text` кекта.
- `tools/kdiff2/allseg.py` — все сегменты всех образов kernelcache.
- `tools/kdiff2/kcptr.py` — декодирование `DYLD_CHAINED_PTR_64_KERNEL_CACHE` (база `0xfffffff007004000`, адрес = `base + (raw & 0x3fffffff)`, работает и для `isAuth=1` — адресная часть та же, подпись не нужна).
- `tools/kdiff2/kstarts.py <kc> <kext> [addr…]` — `LC_FUNCTION_STARTS` кекта (ULEB128-дельты от `__TEXT` образа); по адресу даёт начало и размер функции.
