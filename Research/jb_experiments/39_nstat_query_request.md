# 39. `nstat_client_handle_query_request` (23F84 → 23G83): досягаем из sandbox, изменение — статистика

Дата: 2026-11-27. Объект: iPhone 13 (A15, iOS 26.5.2 / 23F84 → 26.6.1 / 23G83), офлайн-дифф kernelcache; досягаемость — живой прогон из `35`.

Зачем: `27` помечал функцию «кандидат; не разобран» (+блок ~38 инструкций), а `35` закрыл `nstat` целиком. Координатор (`thr_6vcmjuesnu`) заметил, что закрыты только пути **создания** источников, а обработчик запроса — другая функция.

## Поправка к 35 (внесена)

`QUERY_SRC` на устройстве вернул `NSTAT_MSG_TYPE_SUCCESS` — запрос дошёл до диспетчера и обработчика, пройдя по пустой очереди клиента. Отказ (`EPERM`) был только на `ADD_ALL`/`ADD_SRC`. Значит **`nstat_client_handle_query_request` из app sandbox досягаем**; «nstat закрыт» верно для `nstat_ifnet_report_lim_stats` и `nstat_sysinfo_send_data` (работают с источником/подпиской), но не для обработчика запроса.

## Что обработчик делает с телом запроса (исходник `xnu-12377.121.6`, `bsd/net/ntstat.c:7078`)

- `mbuf_copydata(m, 0, sizeof(req), &req)` — копирует **фиксированный** заголовок запроса на стек (`nstat_msg_query_src_req`).
- Из тела используются ровно два поля: `req.srcref` (сравнивается с `nts_srcref` источников в `client->ntc_src_queue`) и `req.hdr.flags`/`req.hdr.context` в `nstat_client_begin_query` (`:7215`): при флаге `CONTINUATION` и новом `context` — `client->ntc_context = context; client->ntc_seq++`.
- Ни один путь не берёт из запроса длину, смещение или указатель. С пустой очередью цикл `TAILQ_FOREACH_SAFE` не выполняется.

## Что изменилось в 23G83

Нормализованный diff: `tools/kdiff2/out/nstatq_fdiff.txt` (2139 → 2028 инструкций, 345 изменённых строк); дизассемблеры `nstatq_23F84.dis`, `nstatq_23G83.dis`. Имя функции в 23G83 подтверждено `kfnames.py` (якорь `nstat_client_handle_query_request`).

Почти весь diff — перестановка блоков и перенос регистров (`x22`→`x25`, `x20`↔`x22`). Одни и те же элементы есть в обеих версиях в одном количестве:

| Элемент | 23F84 | 23G83 |
|---|---|---|
| чтений `hdr.flags` (`[x29,#-0x6a]`) | 4 | 4 |
| записей `client+0x268` (`ntc_context`) | 8 | 8 |
| сбросов `ntc_context` в 0 | 4 | 4 |
| вызовов `ctl_enqueumbuf` (`0xa2e1104` / `0xa2ef7d8`) | 10 | 10 |
| `ldadd` (счётчики статистики) | 16 | 16 |

Содержательное изменение одно, 23G83 `0xfffffff00a0a69e4`:

```
cmn x28, #1            ; x28 = -(partial) из nstat_client_begin_query
mov w8, #0x2ac
mov w9, #0x2a8
csel x8, x9, x8, eq    ; счётчик выбирается по флагу CONTINUATION
add x8, x19, x8 ; ldr w9,[x8] ; add w9,w9,#1 ; str w9,[x8]
```

В 23F84 те же два счётчика инкрементировались раздельно: `+0x2a8` на пути без флага (`0xa09961c`), `+0x2ac` — в другом месте функции (`0xa09a604`). В 23G83 они слиты в один `csel`. Это статистика запросов (`nstat_stats`), к памяти отношения не имеет.

Вывод: **не memory-bug, кандидат закрыт.** Досягаемость при этом реальна, так что если в будущих диффах эта функция изменится содержательно — её стоит смотреть первой.

## Не проверено

- Соответствие полей `+0x268`/`+0x2a8`/`+0x2ac` полям `struct nstat_client` из 121.6 — по косвенным признакам (`ntc_context` пишется/сбрасывается ровно там, где в исходнике, счётчики — `ldadd` рядом с `nstat_stats`), по смещениям структура 26.x не сверялась.
- Остальные «не разобраны» из сетевого кластера `27`: `nstat_ifnet_report_lim_stats` (`cbnz`→`cbz`), `netagent_handle_update_inner`, `tracker_dump`/`tracker_action`, `bpfioctl`/`bpf_setup`. Досягаемость первых двух из sandbox не показана.
