# 42 — Досягаемость AppleMatch (regex sandbox) из приложения: закрыта без приватного entitlement

Дата: 2026-11-27. Только статика, 23G83 (`23G83__iPhone14,5/kernelcache.release.iPhone14,5`, 26.6.1).
Устройства, Basil, серверы не трогались. Продолжение заметки 41 (§7.2–7.3).

> **Поправка после проверки (тот же день):** первая версия заметки называла `0x9bcefd0` «обработчиком `sandbox_init`» и
> считала `x2` буфером профиля из user space. Это неверно: `0x9bcefd0` — MAC-хук **`mpo_cred_label_update_execve`** sandbox
> (слот 18 таблицы `mac_policy_ops` по `0x7f7ebe8`; соседний слот 6 — `mpo_cred_check_label_update_execve` = `0x9bcefc4`;
> выравнивание по открытому `security/mac_policy.h` xnu-12377.121.6, нулевые слоты совпали). Ядро вызывает его при **`execve`**
> (`mac_cred_label_update_execve`, `security/mac_vfs.c`). Разделы ниже переписаны. Главный вывод (свой профиль — только с
> приватным entitlement) проверка подтвердила, но по другой цепочке. Попутно: «GOT не ссылается на AppleMatch» из заметки 41 §3 —
> артефакт моего фильтра, ссылка есть, аутентифицированная (`sandbox __auth_got 0x7f7e570 → 0x8b4329c`).

## 0. Вывод

| Вопрос | Ответ |
|---|---|
| Кто передаёт regex в AppleMatch | Только `com.apple.security.sandbox`, только при **компиляции sandbox-профиля** |
| Может ли приложение передать свой профиль | Только с entitlement `com.apple.private.sandbox.profile` (текст профиля) или `com.apple.private.sandbox.profile:embedded` (по телу `0x9bdd5e0` читает объект `{len, data}`; происхождение данных не прослежено). Проверка — через AMFI (`0x8bb989c`), внутри не разобрана |
| Что это значит для кандидата 41 | На проверенном пути правка grow-буфера в AppleMatch **досягаема из user space только из процесса с этим правом**. Для стороннего приложения путь закрыт; полезен лишь как «kernel-баг внутри Apple-демона» (нужен отдельный вход туда) |
| Spawn-атрибут `posix_spawn` (без права) | **Нет на пути через хук execve** — буфер копируется ядром без проверки права, но в хуке идёт в строки-описания/параметры; в компилятор `0x9bc6170` не попадает (§3). Для 5 других вызывающих компилятора источник буфера не прослежен (§3.1) |
| Готов ли к запуску | Нет. Уязвимость 23F84 в grow-буфере всё ещё не доказана (поле `+0x60`: не установлено, неинициализированное оно или OOB) |

## 1. Цепочка вызовов (23G83)

```
Ядро, при каждом execve → mac_cred_label_update_execve → MAC-хук sandbox 0x9bcefd0 (1303 ins, mpo_cred_label_update_execve)
   │  выбирает профиль: entitlement com.apple.private.sandbox.profile / :embedded → объект (x20), иначе x20 = 0
   ▼
0x9bc590c(buf=x0, kind=w1, &len=x2)   «найти или скомпилировать профиль»
   │  closure на стеке; bl 0x9bc59a4 (таблица профилей, evaluate.c): поиск по ключу, при промахе — callback
   ▼
0x9bc5990: ldp x8,x3,[x0,#0x20]; ldr w2,[x0,#0x30]; b 0x9bc6170
   ▼
0x9bc6170(buf, 0, kind, &len)   0x9bd6fa0(buf,len,&n) — проверка заголовка/версии, tail-call ↓
0x9bc6200 (3191 ins)   разбор сериализованного профиля → 0x9bca058 → AppleMatch 0x8b4329c (regex-компилятор)
```

Ровно два вызывающих ведут в `0x9bc6170`: хвост замыкания `0x9bc5990` (из `0x9bc590c`) и `0x9bcbe8c` (built-in профиль по адресу `0x7f82048`, `0xc4` байта).

Отдельно: `0x9bccb4c → 0x9bccc10` — разбор **уже скомпилированного** профиля (компилятор не трогает).

Компилятор AppleMatch `0x8b4329c` sandbox вызывает через аутентифицированный GOT `0x7f7e570` (`__auth_got`). В первой версии
я сканировал только обычные указатели и потому не видел этой ссылки (поправка к заметке 41 §3).

## 2. Хук execve `mpo_cred_label_update_execve` (`0x9bcefd0`)

Аргументы по `security/mac_policy.h` (xnu-12377.121.6): `x0` = `old_cred`, `x1` = `new_cred`, `x2` = `p`, `x3` = `vp`,
`x4` = `offset`, `x5` = `scriptvp`, `x6` = `vnodelabel`, `x7` = `scriptvnodelabel`; на стеке `execlabel`, `csflags`,
`macpolicyattr`, `macpolicyattrlen`, `disjointp`. В теле: `x22` = `new_cred`, `x21` = `p`, `x23` = `vp`, `x20` = `scriptvp`
(если 0 — `vp`), `x28` = `macpolicyattr`.

Что установлено по телу:
- Выбор профиля начинается с проверки прав: `0x9bd69dc(new_cred, "com.apple.private.sandbox.profile")` (`0x9bcf1f8`),
  затем `":embedded"` (`0x9bcf2d4`, `0x9bcf2f8`, `0x9bcf36c`); `0x9bd69dc` — обёртка над AMFI `0x8bb989c`.
- При наличии права `0x9bdd5e0` читает профиль (`[obj+8]` = длина, `obj+0x10` = данные) — это объект `x20`/`x27`,
  который дальше идёт в замыкание `0x9bc590c` (см. §3).
- Без права: `x20 = 0`, строка-описание `(unnamed)`, далее стандартный путь — профиль из `new_cred`/подписи
  (`0x9badd70([new_cred+0x78])`, `0x9bcf538`) и предопределённые профили по vnode (`0x9bae34c(vp,0,&err)` → `0x9baae88(vp,0/1/2,…)`).
- `invalid spawn attributes` (`0x9bd0384`) — валидация `macpolicyattr` (см. §3).
- `0x9bc3934(p)` — назначение не установлено (битовая маска под блокировкой; похоже на кэш/трассировку).

**Внутри `0x9bcefd0` нет ветки «текст профиля от пользователя без права».**

## 3. Откуда в компилятор приходит буфер (проверено по вызывающим)

Единственный некомпилированный вход в `0x9bc6170` — замыкание `0x9bc590c(buf=x0, kind=w1, &len=x2)`: оно строит closure на стеке,
`0x9bc59a4` (таблица профилей, `evaluate.c`) ищет по ключу и при промахе вызывает хвост `0x9bc5990 → 0x9bc6170(buf, 0, kind, &len)`.
Второй вход — `0x9bcbe8c` (built-in профиль по фиксированному адресу `0x7f82048`, `0xc4` байта).

Все 7 вызовов `0x9bc590c` в кексте (`0x9bbae88` ×2, `0x9bc0f9c` ×2, `0x9bd54bc`, `0x9bdb610`, `0x9bdc83c`) передают `w1 = 0x11` или `4`
(тип), а `x0` — регистр общего назначения (`x20`/`x19`/`x23`) либо локальную структуру на стеке (`0x9bd54bc`, `w1 = 4`,
по-видимому расширения). В 8 инструкциях перед каждым вызовом нет загрузки `x28` (`macpolicyattr`) или строк spawn-атрибута.

Что этим **не** показано: происхождение `x20`/`x19`/`x23` в этих функциях я не прослеживал (кроме `0x9bbae88`, где это тот же
`x20`, что выбран по entitlement'у в §2). Утверждение «в компилятор попадает только профиль из entitlement'а» доказано для
пути через хук `0x9bcefd0`; для остальных вызывающих — по отсутствию видимой связи со spawn-атрибутом, не полным разбором.

Spawn-атрибут (`macpolicyattr` из `posix_spawn`, копируется XNU без проверки права, `spawn_copyin_macpolicyinfo`,
`bsd/kern/kern_exec.c`, ≤ `PAGE_SIZE`) в хуке `0x9bcefd0`: валидируется (`[0]==0`, `[4]==0x450`, `[8]<=0x3f`, `[0xc]<=0x3ff`),
строки терминируются NUL, используются как **строки-описания/параметры** (`0x9bc4598` = `strdup`, `0x9bad3b4` = `snprintf`-обёртка,
`0x9bd1644`/`0x9bda9e0` — применить параметры; компилятор они не вызывают). В `0x9bc590c` не попадают.

**Вывод:** на пути через хук execve (`0x9bcefd0`) свой regex в AppleMatch может передать только процесс с
`com.apple.private.sandbox.profile` (`:embedded`); без права хук идёт к стандартному профилю из подписи/`new_cred` (`0x9badd70`).

### 3.1 Что осталось непроверенным

- Происхождение буфера в 5 из 7 вызовов `0x9bc590c` (`0x9bc0f9c`, `0x9bd54bc`, `0x9bdb610`, `0x9bdc83c`) — не прослежено;
  там может быть иной источник профиля, не связанный с entitlement'ом хука.
- Хук `0x9bcefd0` читал фрагментами; ветки после `0x9bcf538` (профиль из `new_cred`) до конца не прослежены.
- Содержимое `0x8bb989c` (AMFI, проверка entitlement) — не разобрано.
- Какие процессы на 23F84 несут `com.apple.private.sandbox.profile(:embedded)` — не смотрел.
- Дифф `0x9bcefd0` 23F84→23G83 — не делал (она не попала в список изменённых sandbox-функций заметки 41).
