# Открытые вопросы и следующие шаги

## Открытые вопросы

1. **Почему на Basil закрыт `task_for_pid`, хотя `kernel-cfw-task_for_pid` применён.** Дополнение (`09_…md`): патч NOP-ит только ранний гейт `pid == 0` (`cbz w23`), а за ним остаётся второй — `task_conversion_eval_internal` (`kernel-boot-task_conversion_eval`, тоже применён). Прочитать байты в живом ядре не удалось: `process.dump` → `mach_vm_remap: 57`, `kcall10` без слайда бесполезен. Нужно перезапустить Basil с `--kernel-debug-port` и читать через LLDB. Варианты: патч снимает другую проверку (например, для root или для entitlement `com.apple.system-task-ports`), а не ту, что отвечает приложению; либо сигнатура патча не совпала на 24B119, и он применён «формально». Проверка: прочитать байты по сайту патча в дампе памяти Basil и сравнить с файлом; вызвать `task_for_pid` из root-сессии `vphoned`.
   Дополнение после отчёта V1: в `Research/KernelCustomFirmwarePatches/patch_task_conversion_eval_internal.md` (A3) описан второй гейт — `cmp X9,X0` → `cmp xzr,xzr` в `task_conversion_eval_internal` (адрес в заметке — для билда с базой `0xfffffe00…`, не для 24B119). Это кандидат на «ту самую» проверку, которую снимает `kernel-cfw-task_for_pid`.
2. **Код политики `task_for_pid` одинаковый на A15 и A19, но сигнатура vphone не находится ни там, ни там.** К какому билду она написана — не установлено.

**MPTCP (CVE-2026-86962) — живой прогон, заметка 22 §11.** Решение владельца: «Hydra наружу».

Проверено по pcap `tools/mptcp_live/live_run_20261127/hydra/v4.pcap` (49 пакетов, собственный разбор заголовков) и листингу `mptcp_validate_csum` 24B156 (`/tmp/jbresearch/mptcp_fix/vc_24B156.dis`, адреса взяты из листинга).

**Бинарник 24B156, путь сбоя в `mptcp_validate_csum`.**
- `0xfffffe000b04226c orr w9,w10,#0x200000` → `0xb042270 str w9,[x8,#0x404]`: `TMPF_SND_MPFAIL` ставится на **tcpcb подпотока** (x8 = первый аргумент).
- `0xb042274 ldr x8,[x8,#0xa8]` → `0xb042278 ldr x8,[x8,#0x40]` → `0xb04227c cbz` → `0xb042280 ldr x9,[x8,#0x18]` → `0xb042284 ldr x9,[x9,#0x30]` → `0xb04228c ldr w10,[x9,#0x404]` → `0xb042290 tbnz w10,#0x10` (fallback уже стоит — уйти) → `0xb042294..0xb0422a4`: очистить биты `#0xfff6fffb`, поставить `#0x10000` → `str w10,[x9,#0x404]`. Это в точности тело `mptcp_notify_mpfail`: `TCP_FALLBACK` (`0x10000`) ставится на **tcpcb другого сокета** (переход по полям — как `socket → inpcb → tcpcb` родителя).
- `0xb0422b0 bl 0xfffffe000b1cca08, w1=0x10001` = `soevent(so, SO_FILT_HINT_LOCKED | SO_FILT_HINT_MPSTATUS)`.
- затем `m_freem` (`0xb0422bc`), счётчик bad csum (`0xb0422c4..d0`), возврат `-1`.

**Исходник `xnu-12377.121.6`.** `mptcp.c:1211–1216`: `tp->t_mpflags |= TMPF_SND_MPFAIL; mptcp_notify_mpfail(tp->t_inpcb->inp_socket);` — флаг на `tp`, fallback — внутри `mptcp_notify_mpfail` на `intotcpcb(sotoinpcb(so))` (`mptcp_subr.c:6016–6021`). `mptcp_opt.c:365–367`: `if (tp->t_mpflags & TMPF_TCP_FALLBACK) { if (tp->t_mpflags & TMPF_SND_MPFAIL) mptcp_send_mpfail(tp, …) }` — **оба флага проверяются на одном `tp`**.

**Вывод.** После сбоя контрольной суммы `SND_MPFAIL` оказывается на подпотоке, а `TCP_FALLBACK` — на родителе; условие отправки `MP_FAIL` на одном `tp` не выполняется. Это объясняет отсутствие `MP_FAIL` в pcap без ссылки на «FIN закрыл сессию». Прежняя гипотеза (§11 заметки 22) снята.

Оговорки: (1) адреса переходов `+0xa8/+0x40/+0x18/+0x30` прочитаны по форме кода и сопоставлены с исходником, символов в бинарнике нет; (2) не проверял, есть ли в 24B156 другой путь, ставящий `SND_MPFAIL` на родительский `tp` (в исходнике `mptcp.c:1215` — единственная точка установки); (3) константы `0x200000`/`0x10000` соответствуют `TMPF_SND_MPFAIL`/`TMPF_TCP_FALLBACK` из `tcp_var.h:765` OSS — смещения полей в 24B156 приняты по совпадению формы с OSS.

**Что это меняет для живого теста.** Отсутствие `MP_FAIL` — не признак того, что триггер не обработан: по бинарнику `mptcp_validate_csum` отработал, флаги выставлены, данные отброшены (`EAGAIN` приложению). Паники нет при `DATA_FIN=0` — согласуется со статикой B (без DFIN mbuf извлекается до validate). Для проверки пути с `DATA_FIN=1` это изменение ничего не даёт — этот режим по-прежнему запрещён.
