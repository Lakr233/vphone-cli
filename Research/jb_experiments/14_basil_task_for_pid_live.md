Ответ на вопрос 1 (кратко): оба патча применены фактически, но ни один не затрагивает инструкцию, которая отказывает root.
`kernel-cfw-task_for_pid` NOP-ит `cbz w24` по `pid==0` (S1). Отказ root идёт из `cbnz w0` после вызова MACF-политики
(S3) — она не пропатчена ни одним патчем vphone. Один и тот же NOP подходит всем трём билдам.

## 3. Почему именно S3, а не другие места (по коду, три билда)

`task_for_pid` для root идёт так:

1. **S1** `cbz w24` — проверка `pid==0`. Для обычного pid не срабатывает, патч на путь root не влияет.
2. `proc_find`, `proc_refonce` — `kr=5` при отсутствии процесса (`0x91de304` Basil, `0xa305778` 23F84): это не гейт прав.
3. **`task_for_pid_posix_check`** — для root проходит: тело читает `cr_uid` из ucred (`ldr w22,[x20,#0x18]`),
   `cbz w22 → return 1`. Basil/23F84: вызов идёт на 4-инструкционный thunk `0x91de54c` / `0xa3059a4`
   (`ldr w8,[x0,#0x64]; cmp w8,#5; b.ne; mov w0,#0; ret`), который при `[p+0x64]==5` вернёт `0`, иначе проваливается
   в настоящее тело `0x91de560` / `0xa3059bc` (тело возвращает `1` при `cr_uid==0` — `0x91de64c`). На 24B156 та же
   проверка встроена в начало тела `0xb151778`.
   Это **не** гейт суперпользователя; согласуется с S6 «posix_check root пропускает».
   (Что именно значит `[p+0x64]==5` для живого процесса-цели — не проверял, `ГИПОТЕЗА`: состояние процесса.)
4. **S3** `bl mac_proc_check_get_task; cbnz w0 → kr=5`. Параметры по Basil: `x0=&x26` (ucred вызывающего),
   `x1=sp` (`struct proc_ident`), `w2=0` (flavor). Это MACF-диспетчер: та же функция на трёх билдах
   (одинаковый пролог на трёх билдах, 3 аргумента; читает флаг `[0x77b6ee4]` и указатель `[0x77b6ef0]`, затем цикл по
   списку политик; имя флага по исходникам не сверял — `ГИПОТЕЗА`: enforcement-флаг этой проверки).
5. **S2** `bl 0x91de66c` → при возврате ровно `0x10004005` → `kr=0xe` (`0x91de4f8`), иначе управление
   уходит на `0x91de280` — то есть **снова через S3**. Поэтому даже «успех» conversion не обходит MACF.
   Что это за вызов (по коду, не по метке патчера): `0x91de66c` — трамплин `b 0x8d8d3a8`; там читается указатель
   из глобального слота (`adrp x8; ldr x8,[x8,#0x8a0]`), складывается аргументная структура и идёт `bl 0x8d04a08`.
   `ГИПОТЕЗА`: адресат — hook MACF-политики, а `0x10004005` — его код отказа. Слот в файле нулевой (заполняется при загрузке).
   Патч `kernel-boot-task_conversion_eval` сидит **в другой функции**, `0x8d086d8` (foff `0x1d047a8`): он заменяет
   `cmp x0,x9` (`x9` читается из глобального слота `0x77b3c58`) на `cmp xzr,xzr`, отчего `b.eq 0x8d087e4` выполняется
   всегда и функция возвращает `x0 = w8` **без двух дальнейших вызовов**; `w8` при этом — то, что осталось от
   входных проверок (`0x23` при `x1==0`, иначе — входное значение). Что это значит для вызова из `task_for_pid` — п. 3 раздела 7.

Пункты 4–5 согласуются с S6 и с живым наблюдением соседа (`w23=5` после S3, `w23=0xe` после S2).

Расхождение S6, которое осталось: S6 пишет, что отказ `task_conversion_eval` даёт `kr=0` + `MACH_PORT_DEAD`.
По коду возврат `0x10004005` даёт `kr=0xe`, а прочие ненулевые возвраты уходят на путь «успеха» и упираются в S3.
Происхождение `0x10004005` из кода не выводится — `ГИПОТЕЗА`: код MACF-политики, константу по исходникам не сверял.
На итог для root это не влияет: S3 стоит на обоих путях.

## 4. Что дают `kernel-cfw-debugger` и `kernel-cfw-proc_pidinfo` (по байтам в образе Basil)

Оба применены (раздел 2.1). Про процессы они ничего не «дают»:

- **`kernel-cfw-debugger`**: `_PE_i_can_has_debugger` заменён на `mov x0,#1; ret` — ядро всегда отвечает
  «отладчик включён». Это состояние отладчика, не права процесса. Энтайтлмента процессу не добавляет.
- **`kernel-cfw-proc_pidinfo`**: два NOP-а вместо `cbz x0` и `cbz w19` перед `mov w0,#0x16` (`EINVAL`) — снимают
  только запрет на `flavor` для `pid==0`. Процесс остаётся со своим ucred.

Процесс root в госте — это состояние ucred (`uid==0`), которое даёт загрузка/окружение гостя, а не эти патчи.
Они не связаны с гейтом S3 и не могут его обойти. Запрос «read the gate bytes» для `task_for_pid` закрыт разделом 2.

## 5. Инцидент 26.11 21:52: мной уронена Basil (boot M)

- **Что вызвал:** из шелла госта `/private/var/tmp/kx fffffe003550ea78` — kcall10 на адрес
  `mov w0,#1; ret` (link `0xfffffe0008cd8a78`) + слайд. Это был «selftest» из заметки 13, повторённый мной.
- **Почему упало:** адрес набран вручную. Верный для boot M: `0x8cd8a78 + 0x29840000 = 0xfffffe0032518a78`.
  Я вбил `0xfffffe003550ea78` — на `0x2ff6000` дальше, мимо кода. Итог: `Kernel instruction fetch abort at pc 0xfffffe003550ea78`,
  panicked task `pid 966: kx`. `kslide.py` считает `link + slide` в коде; я его обошёл ручным вводом.
- **Моя неверная версия (снята):** сначала я написал родителю и соседу, что у Basil «разные слайды у сегментов»
  (`0x29840000` у заголовка, `0x2b4e4000` у `__TEXT_EXEC`) и что инструмент/сверка соседа могли читать не по тем адресам.
  **Это неверно.** Строка `Kernel text exec slide 0x2b4e4000` в panic-логе напечатана от другой link-базы
  (`0x8ca4000`), а не второй слайд. Слайд `0x29840000` верен для всего образа; это видно по `lr 0xfffffe00324e7850`
  и `x8 …324e7804` в том же panic-логе. Правильное исправление отправлено обоим, родитель принял.
- **Не путать адреса в логе:** `pc 0xfffffe003550ea78` — адрес сбоя (то, что я вызвал). `0x000000010450027c` — последний
  кадр user-space (возврат в процесс `kx`, `fp: 0`), а не место сбоя. Гость прожил ~272 с (`last started kext at 272380563`).
- **Состояние:** VM-процесс жив (pid 56569), гость в панике; Sileo (pid 96764) и GDB-stub сессия соседа на этой VM
  остановлены. Я Basil не перезапускал, патчи не менял. После этого — запрет на любые обращения к Basil и kcall10.
- **Файлы:** `tools/tfp_gates/Basil-panic-after-my-kx-215244.log` (копия), `tools/tfp_gates/selftest.txt` (вызванная строка).

## 6. Инструменты и как воспроизвести

`Research/jb_experiments/tools/tfp_gates/` (самодостаточно, нужен python3 + capstone):

- `kdiff.py` — загрузка `com.apple.kernel` из kernelcache (файл, base, секции с foff); копия `/tmp/jbresearch/igmp/kdiff.py`.

- `tfp_gates.py <kc> <task_for_pid VA> [n] [out]` — полный листинг с foff и байтами.
- `findtfp.py <kc>` — ищет `task_for_pid` по строке `proc_ro_ref_task`; работает на 23F84/24B156
  (S1 и все пары `bl; cbnz w0`); **на Basil выдаёт S1 = None** — там `task_for_pid` задавать явно через `tfp_gates.py`.
- `tfp_basil.dis`, `tfp_23F84.dis`, `tfp_24B156.dis` — листинги, из которых взята таблица.

## 7. Открытое

1. Закрыто чужим чтением: координатор сверил в памяти (boot N и boot O) `0x91de128/268/26c/2bc` и `0x8d087a8` с файлом.
   Своего живого чтения нет и не будет без отдельного разрешения.
2. Живой `task_for_pid` от root на живой процесс: ожидание по коду — `kr=5`, причина S3. Не измерено здесь.
3. Имена вызываемых (`mac_proc_check_get_task`, `task_conversion_eval`) присвоены по структуре кода и логу патчера,
   не по символам. Для MACF-диспетчера (S3) форма одинакова на трёх билдах. Не установлено: точная семантика функции
   `0x8d086d8` (проверка диапазона указателя в тексте ядра, таблица типов `& 0x3ff`, `cmp x0,x1`, `cbnz w3`) и то,
   что она возвращает после патча для реального вызова из `task_for_pid`; `ГИПОТЕЗА`: XNU `task_conversion_eval_internal`,
   где `cmp x0,x9` — сравнение вызывающего с `kernel_task`. Нужна сверка с исходниками XNU для 27.2 и живой прогон.
4. Будет ли NOP на S3 достаточным на практике (AMFI/`cs_enforcement` по пути `convert_task_to_port` и т. п.) —
   вне этой заметки: S6 и код показывают, что других `kr=5` для root в самой функции нет.
